一个人的研发部门

当 AI 成为我的同事

从独立开发到多智能体协作，一次关于个人生产力与研发方式的探索。

在开发 KeyGuard 的过程中，我逐渐开始使用不同的 AI 工具：有人负责产品策划，有人负责视觉设计，有人编写代码，还有人负责独立审查。

但随着工具越来越多，一个新的问题出现了：面对如此众多的 AI 产品，我们究竟应该如何选择？它们之间有什么区别？为什么有些任务适合交给 Gemini，有些任务却更适合交给 Codex？

这篇文章将从大语言模型（LLM，即 Large Language Model，大语言模型）的技术演进出发，结合主流 AI 工具的能力定位、公开评测数据，以及我在北辰实验室的真实开发经历，尝试回答这些问题。

我想探索的，不是哪一个 AI 最强，而是一个普通人如何将不同的 AI 组织起来，构建属于自己的研发体系。

00 / PROLOGUE

一个人的研发部门

本文所有事实、评测与推断均按来源性质标注，阅读时请注意区分。

2026 年，各家发布稿里出现频率最高的词，不再是「参数量」。它变成了 Harness（支持智能体调用工具、管理上下文并执行流程的软件框架）、子智能体（负责子任务的智能体）、上下文（当前任务的对话与资料）压缩。

过去九年，大模型的能力叙事有三次转向：先是规模（2017—2021），再是对齐与对话（2022—2023）， 然后是推理与软件工程（2023—2025）。进入 2026 年，部分行业叙事开始更多关注「模型外围的系统」：工具、上下文、多智能体与 Harness。这是一种观察视角，不代表整个行业已完成统一转向。

能力的增长点从「模型本身」（规模、对齐、推理）逐步转到「模型外围的系统」（工具、上下文、多智能体、Harness）。 2026 年各家发布稿里，「Harness」「子智能体」「上下文压缩」出现的频率明显高于前几年。 —— 本资料包对 2026 年发布语料的归纳 推断

这条主线解释了为什么「一个人的研发部门」在今天成为可能：当一个模型被放进不同的 Harness 里， 它的实际表现可以差出三倍；而当多个 Harness 被一个人编排起来，一个人就可以覆盖过去需要一个小团队才能覆盖的环节。

数据使用三条规则

本文严格遵循以下规则，读者也可以用它们来校验文中每一个数字：

  1. 不同评测版本不能混用。Terminal-Bench 2.0、2.1、4.0、4.1 是不同题集；HLE、HLE-Diamond、HLE（纯文本子集）、HLE（带工具）也不是同一个口径。
  2. 同一评测，Harness 不同也不能直接对比。同一模型在不同 Agent 框架里的分数可能差好几倍。
  3. 推理档位要标出来。2026 年的模型普遍有 low / medium / high / xhigh / max 等档位，同一模型不同档位分数和成本差异很大。

02 / DEFINITIONS

模型、应用、Agent 与 Harness

四个层级 · 一组可引用的权威定义

在讨论「一个人能不能干一个部门的活」之前，先要把四个常被混用的词分开：大语言模型（LLM，即 Large Language Model）、AI 应用、编程 Agent（能调用工具并多步执行任务的智能体）、Agent Harness（支撑智能体运行的软件框架，也称“脚手架”）。

英国 AI 安全研究所在 2023 年把 AI Agent 描述为「模型 + 脚手架」（Harness，负责工具调用、上下文和执行流程的软件层）。LangChain 的说法更直接： 「Agent = Model + Harness……不是模型的部分，就是 Harness。」

四层技术分层

从最内层的神经网络权重，到最外层面向用户的产品界面。悬停或点击任意层级查看对应说明。

L1

大语言模型 LLM

训练好的神经网络权重，输入 token、输出 token。

代表：GPT-6.2 Astra、Gemini 4 Carbon、DeepSeek-V4-Pro、Qwen4-Max 接触方式：API 边界：本身不会执行代码，也不会记住上一次对话
L2

AI 应用 Application

面向终端用户的产品，把模型包装成对话、搜索或办公工具。

代表：ChatGPT、Gemini App、DeepSeek App、Qwen App 接触方式：网页 / App 边界：重点在交互体验、记忆、联网和文件处理
L3

编程 Agent Coding Agent

专门面向软件开发、能读写代码库并执行命令的 Agent 产品。

代表：Codex、Cursor Agent、Qwen Code、Google Antigravity 接触方式：IDE / CLI / 云端 边界：能自主完成多步编程任务，并产出 PR
L4

Agent Harness Scaffolding

让模型变成 Agent 的那层工程系统：循环、工具、沙箱、上下文、权限、子智能体。

代表：DeepSeek Harness、Qwen Code 1.0、Codex CLI、Claude Code、CodeRabbit 的审查 Harness 接触方式：开发者配置 边界：决定同一个模型能发挥出多少能力

来源性质：事实 定义引自 Wikipedia、LangChain、Nielsen Norman Group、Google Cloud、DeepSeek Harness 首页与 Qwen Code 文档。 推断 「编程 Agent ≈ Harness + 模型 + 界面」为本资料对上述定义的整合。很多产品同时处在两层，比如 Qwen Code 1.0 官方把自己称为「开源 Harness」，同时它也是一个编程 Agent 产品。

这四层的关系不是并列，而是嵌套。同一个模型换一层 Harness，表现可以差出数倍—— 这正是第 05 节「Harness 效应」要展示的东西。

OpenAI GPT-6.2 Astra / Sol

产品分层很清楚：Astra 面向「最难项目」，Sol 面向「日常工作」。两者都在 ChatGPT Work、Codex 和 API 中提供。 Astra 的输入输出单价比 GPT-6 Astra 低 20%，缓存输入低 60%；Sol 沿用 GPT-6.1 Sol 的价格。

官方建议保持提示词前缀不变、把新指令追加在后面，以提高缓存命中率——这是上下文管理直接影响成本的最直观例子。

事实 官方同时披露了局限：在两项对齐测试中，这两个模型更容易「不提及阻碍工作的障碍」， 比如文件缺失或搜索工具不可用。OpenAI 已在 Codex 中加入指令来减少这种情况。

Google Gemini 4 Carbon / Neon

Carbon 被 Google 称为「最强模型」，主打网络安全和长周期 Agent 能力，先通过 Fairwind 计划提供给网络安全防御者， 之后才全面开放。Neon 主打「前沿智能 + 快速端到端完成任务」，有四档思考级别，可在 Antigravity 中作为编排者调度并行的 Hydrogen 子智能体。

推断 Carbon 是「能力上限」，Neon 是「速度与成本平衡」。 但要注意：Neon 在 Artificial Analysis 智能指数上反而比 Carbon 略高（61 对 60），写作时不要简单地说「Carbon 全面强于 Neon」。

DeepSeek-V4 系列

技术报告显示，V4-Pro 总参数 1.6T、激活 49B；V4-Flash 总参数 284B、激活 13B，均为 MoE 架构，支持 1M 上下文。 架构上是混合注意力（压缩稀疏注意力 CSA + 重度压缩注意力 HCA）：在 1M 上下文下，V4-Pro 的单 token 推理 FLOPs 只有 V3.2 的 27%，KV Cache 只有 10%。

精度上，MoE 专家参数用 FP4，其余大部分参数用 FP8；权重采用 MIT 许可证。推理档位为 low / high / max 三档。 产品化方面，V4-Pro 正式版原生支持 OpenAI Responses API 并专门适配 Codex。

阿里 Qwen4-Max

2.4T 主干参数，每 token 激活 71B，另有 328B 的 N-gram Embedding 参数；原生视觉能力；1M 上下文。 官方称 2.4T 规模的训练「全程没有 loss spike」。

官方评测 自建 Work360 基准（26 个一级领域、721 个三级专业领域）得分 52.69， 上一代 Qwen3.8-Max 为 47.74；每任务平均成本从 $4.43 降到 $1.67（降低 62%）。 二手汇总 第三方解读文章指出，Qwen4-Max 发布表中的 16 项评测有 10 项是阿里自己跑的。

这里最容易被忽略的一层是「模型池」。同一任务里，编排者可以给不同的子智能体分配不同的模型： 检索用便宜的、代码用最强的、审查用另一家的——这本身就是一种交叉验证。

Agent Harness 是包裹在大语言模型外层、让它可以以 AI Agent 身份运行的软件基础设施，负责工具使用、提示词、记忆、状态持久化、权限、错误处理、执行环境和反馈循环。 —— Wikipedia「Agent Harness」条目 事实

08 / COLLABORATION

人工协作 vs Agent 协作

流程变了，但责任没有消失，只是换了位置

把两条流程并排放，差异不在于「谁更快」，而在于「谁在什么位置上」。

右侧 Agent 协作流程是概念示意。北辰实验室目前仍由人分配任务、传递资料并验收结果，尚未实现统一的自动调度系统。

人类协作串行，上下文在人与人之间丢失

每一环都是一个人。切换成本高，审查常常是瓶颈。

  • 阅读代码库理解现有结构、依赖与约定
  • 编写实现单线程，边写边查
  • 自测作者自测，视角单一
  • 提交 PR等待排期
  • 同事审查审查者需要重新建立上下文——这是最贵的一步
  • 返工与合并来回沟通，上下文再次丢失

Agent 协作 · 概念示意满足依赖条件后并行

在具备可靠编排、权限边界与质量关卡的系统中，部分中间任务可交由子智能体并行；人仍需定义目标、处理例外并验收结果。

  • 定义目标与验收标准人。这是唯一不可外包的环节
  • 主 Agent 拆解任务生成子任务与依赖关系
  • 并行：代码 / 审查 / 测试 / 检索不同子智能体，可分配不同模型
  • 上下文压缩与汇总长会话中由 Harness 负责状态持久化
  • 冲突消解与交叉验证审查 Agent 不写代码，保证独立性
  • 人验收回到人的位置，但这次是判断而不是执行
必须写进来的反例。 2025 年 7 月 10 日，METR 公布了一份随机对照试验：资深开发者使用 AI 后，完成任务反而慢了 19% 事实。 这是第一份严格的反直觉证据，提醒读者不要高估 AI 带来的提效。

所以「一个人 + 一组 Agent」成立的前提，不是 AI 一定更快，而是 任务被切分到了 Agent 擅长的粒度上——可验证、可并行、上下文边界清晰。 切分错了，编排成本会吃掉全部收益。
09 / REFLECTION

不是找最强的 AI，而是组织合适的协作

选择 AI 不仅取决于模型能力，也取决于工具环境、任务类型、上下文管理及交付方式。

在 KeyGuard 和这篇专题的实践中，我逐渐体会到：工具的价值来自它是否适合当前任务，也来自人能否提供清晰目标、检查过程并承担最终判断。把 AI 放在合适的位置，比追逐一个总排名更重要。

目前的协作仍由人明确目标、分配工作并审阅结果。文章中关于多个 Agent 自动编排的流程是概念说明，并非北辰实验室已经实现的自动化研发系统。

01 · 等待时间

资料调查与初稿优化若都依据同一份原始目标，可以评估并行开展；网页终稿仍依赖已确认的文章内容。并行只能缩短彼此独立部分的等待，不能消除人工检查与交接时间。

02 · 信息漂移

多次转述就像“可乐图标”在 A、B、C、D 之间传递，越到后面越可能偏离原意。可行的控制方式是保留不可覆盖的原始需求、事实来源和已批准决策；每个执行者同时读取这些基准，GPT 做差异审查而非每轮重写全文，偏离时再退回修正。

03 · 自动化边界

后续可用任务依赖图（DAG，即描述任务先后关系的有向图）编排独立任务，记录状态、开始与结束时间、交付物和失败原因，并在人需要决策时暂停等待。这里是下一步探索方向，不代表已经实现或验证。
